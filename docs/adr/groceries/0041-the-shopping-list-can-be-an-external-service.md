# The shopping list can be an external service, reached by a one-way handoff

A household that shops with Bring! wants Norish's "add to groceries" to put the ingredients in Bring!, and Bring! gives no way to do that: there is no endpoint that takes items, only a recipe import that takes the address of a page, and Bring!'s own servers fetch that page. We chose a one-way **Bring Handoff** through a temporary unauthenticated page. For each send the server stores the lines under a 192-bit random token (24 bytes, base64url) in Valkey for one hour, serves them at a public `/share/bring/<token>` as a schema.org Recipe, and asks Bring! for the deeplink that imports that address. The page exposes a title, the servings and the item lines and nothing else: no user, household, recipe id or link, and never the recipe's own media, since its image is the static Norish icon. The record is not deleted on read, because it is unknown whether Bring! fetches once or again later; the hour is the only bound. An instance Bring!'s servers cannot reach, which is one without an HTTPS `AUTH_URL` or whose address is or resolves to a private one, is refused before any request is made, and says so. The check is skipped only when `BRING_API_URL` points somewhere other than Bring!'s own address, which means a test double or a proxy stands in for it; `ALLOW_PRIVATE_ADDRESSES` plays no part, because it only seeds the page-renderer setting.

The **Shopping List Provider** is an instance setting, `builtin` or `bring`, and the switch is made in the user interface only. In Bring mode the Groceries tab and pages go and every add-to-groceries path sends to Bring!; no grocery data is deleted, the server still accepts grocery writes, the public groceries API and recurring groceries are untouched, and the offline replay of grocery mutations is untouched. Switching back is therefore lossless: the list is exactly what it was. The Pantry is consulted as before, once, when a recipe is added, because it decides which lines are sent.

On the web the deeplink arrives after an asynchronous call, and a browser opens a tab only inside a tap, so the press itself opens a blank tab and the tab is sent to the link once it is back (or closed when the send fails); only where the browser refused even that tab does the send end in a toast with **Open Bring!**. An app that may open another app unprompted opens the link directly. `bring.send` is the one grocery-adjacent write that is never queued offline: a replayed send would hand Bring! a link whose page expired while the phone was out of signal.

The trade-off is deliberate: the household's list now lives where Norish cannot see it. Nothing is read back, nothing is kept in step, and Norish's prices, aisles and shared ticking do not apply to Bring!'s list. The instance must also be reachable from the internet, which a LAN-only install is not.

Rejected: **blocking grocery writes** while Bring! is chosen, which would break the public API, recurring groceries and offline replay for a setting that only changes where new ingredients go, and make switching back lossy or an error; **a database table** for handoffs, which needs a migration and a sweeper for a record that is worth an hour; **exposing the real recipe share link**, which would publish the recipe, its media and its author to a third party and ties the list to a recipe someone may later unshare; and **opening the link from the async answer on the web**, which a popup blocker defeats; the tab is opened blank in the press instead.

## Consequences

- The setting is the `grocery_list_provider` configuration key, announced on change like the other general settings; every client reads it, and the server rereads it in `bring.send`, so a stale client cannot send on an instance that switched back.
- A handoff record is `{title, servings, lines, createdAt}`; it carries no identifier of anyone, and neither the token nor the page address is logged.
- A person may send thirty times in ten minutes; further sends return `rate-limited`. A send is counted only once it has passed the provider, recipe-access and reachability checks, so a refusal that costs nothing does not use up the quota. A handoff whose deeplink Bring! did not give is deleted at once.
- Bring! thereby also sees the instance's public address, and anyone holding the temporary link can read the lines until it expires after an hour.
- Asking for the deeplink does not prove that Bring! can read the page: Bring! fetches it only when the link is opened, through its recipe parser (`GET /rest/bringrecipes/parser?url=`), and a failure there shows only Bring!'s own "not a valid recipe". So the server calls that parser itself before it asks for the deeplink. When the parser could not fetch the page the send answers `page-unreachable` with the HTTP status the instance gave it, which names a reverse proxy, login or bot check standing in front of `/share/bring/`; when it fetched the page and found no recipe, `bring-rejected`.
- Only an `https` deeplink is accepted from Bring!'s own API (`http` only from a configured `BRING_API_URL`), and both apps' `openExternalUrl` refuse any scheme but `http` and `https`.
- Lines are sent with the unit written short in the reader's language, as the interface writes it (`250 g flour`, not the stored `gram`), because Bring! parses that best; an item with no usable name is left out and a send carries at most 150 lines.
- Expected failures are returned as a reason (`not-bring`, `not-public`, `page-unreachable`, `bring-unreachable`, `bring-rejected`, `rate-limited`), not thrown, so each has its own message.
- `BRING_API_URL` exists only so a test can stand in for Bring!; the default is Bring!'s own address, and Bring!'s deeplink and parser endpoints are undocumented, so `bring-client.ts` is the one place that knows their shape.
- The mobile app ignores the setting in this release. Its platform adapter says `supportsExternalShoppingList: false`, and the shared `useGroceryListProvider` then answers `builtin` without asking the instance, so the groceries tab, the add screens and the pantry keep the built-in list and its wording exactly as before. The gate is lifted when the app hides its tab, redirects its groceries stack and relabels its add screens.
- A later external provider is a new value of the setting and its own handoff, not a generalisation of this one.
